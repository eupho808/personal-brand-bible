## 4. Personal Story

I grew up in Russia, studying in college, with a clear disadvantage in English and no budget for tutors or premium courses. Instead of accepting that gap, I began building tools to close it. That led to AI English Journey — a product created not for a market, but for myself.

Along the way, I discovered that my real strength is not writing code by hand. It is seeing problems, designing solutions, and using AI to build them. I am not a classical developer. I am a Product Builder who works in an AI-first way.

Every project in this ecosystem comes from a real need. WalletGuard Pro came from a real concern about crypto security. AI English Journey came from my own language struggle. AI Project Architect Design came from the need to structure ideas into real products.

The story is not "I want to get into university." The story is "I encountered real problems, designed solutions, and shipped products — and university is the next step in that journey."

## 5. Core Values

1. **Authenticity over performance.** Every project must solve a real problem I actually care about.
2. **Quality over quantity.** One world-class project is more valuable than ten average ones.
3. **Clarity over cleverness.** Every message, interface, and document must be easy to understand.
4. **Consistency over novelty.** The ecosystem must feel like one company, not a collection of experiments.
5. **Long-term thinking.** Decisions are judged by whether they still look good in three years.
6. **Resourcefulness.** Limited budget is not an excuse. It is a constraint that forces better decisions.
7. **AI as amplifier, not replacement.** AI tools extend my ability to design, write, and ship — but the product thinking is mine.

## 6. Principles

### 6.1 Engineering Principles

- **AI as augmentation, not replacement.** AI helps implement, but product thinking is human.
- **Offline first.** Products should work without constant connectivity when possible.
- **Privacy first.** User data stays local unless explicitly shared.
- **Simple beats clever.** Prefer clear solutions over impressive complexity.
- **Readable beats short.** Code and documentation must be understandable.
- **Documentation is code.** If it is not documented, it is not done.
- **Systems over hacks.** Build reusable patterns, not one-time fixes.

### 6.2 Product Principles

- **Never build features before validating the problem.** Every feature must solve a real need.
- **One solved problem is better than ten unfinished ideas.** Finish before starting new things.
- **Software should reduce cognitive load.** Interfaces should be obvious, not impressive.
- **The user is a real person.** Design for actual behavior, not ideal scenarios.
- **Ship small, ship often.** A working MVP is more valuable than a perfect plan.

### 6.3 Learning Principles

- **Every project must teach something new.** If there is no new skill, the project is not worth building.
- **Document every important lesson.** Knowledge compounds when it is written down.
- **Mistakes become documentation.** What went wrong is as valuable as what went right.
- **Teach to learn.** Explaining a concept in writing reveals gaps in understanding.
- **Knowledge compounds.** Small consistent learnings add up over years.

### 6.4 Decision-Making Principles

Before any major decision, ask:

- Does this strengthen my portfolio?
- Will this look professional to an admission committee?
- Does it fit the overall ecosystem?
- Is it authentic to my story?
- Will it still look good in three years?

If the answer to any of these is unclear, pause and revisit.

### 6.5 Quality Standards

- Every public repository must have a complete README.
- Every project must have a clear problem statement.
- Every visual asset must follow the design system.
- Every text must be natural, clear, and free of clichés.
- Every shipped product must feel finished, even if the feature set is small.

### 6.6 What We Never Build

- Projects created only to impress universities.
- Features that do not solve a real problem.
- Cluttered interfaces.
- README files that say "This is my portfolio project."
- Copy that sounds like generic marketing.
- Logos, colors, or layouts that do not match the design system.

### 6.7 Anti-Goals

I do **not** optimize for:

- Viral GitHub stars.
- AI hype.
- Flashy landing pages.
- Fake productivity.
- Empty certificates.
- The approval of people who do not understand the work.

I **do** optimize for:

- Real products that solve real problems.
- Deep understanding of what I build.
- Consistency over time.
- Clear documentation.
- Long-term growth.
- Work I can explain honestly.

# IDENTITY

## 15. Personal Identity

I am an AI Product Builder.

I do not primarily write code by hand. I identify problems, design products, architect solutions, and use artificial intelligence to implement them efficiently.

I am also:

- A self-directed learner.
- A systems thinker.
- A design-sensitive builder.

## 16. Positioning

Avoid: Junior Developer, Frontend Developer, Backend Developer, Coder.

Prefer:

- AI Product Builder
- AI Product Designer
- Product Creator
- AI-powered Product Developer

Use these consistently in bios, headlines, and introductions.

## 17. Brand Personality

If this brand were a person, it would be:

- Calm and confident
- Curious and self-improving
- Minimalist and precise
- Honest about limitations
- Ambitious without arrogance

Not: loud, flashy, corporate, or overly casual.

## 18. Product Philosophy

Every project begins with a real problem. Not a tutorial. Not a trend. Not a university requirement.

The process:

1. Identify a real problem from my own experience.
2. Define the ideal solution without worrying about implementation.
3. Design the user experience and architecture.
4. Use AI tools to build, test, and iterate.
5. Document and publish with professional presentation.

A project is not finished when the code works. It is finished when the story, design, and documentation are complete.

## 19. AI Usage Principles

- AI is a tool for implementation, not a replacement for thinking.
- I design the product. AI helps me write, code, and visualize.
- I am transparent about using AI where appropriate.
- I validate AI-generated output before publishing.
- I continuously improve my prompts and workflows.

# VOICE

## 20. Tone of Voice

- Clear and direct
- Confident but not arrogant
- Curious and thoughtful
- Professional but human
- Minimalist in expression

Avoid hype, exaggeration, and generic marketing language.

## 21. Writing Style

- Use natural English.
- Write short, purposeful sentences.
- Avoid clichés: "revolutionary," "game-changing," "leverage," "synergy."
- Avoid filler and vague claims.
- Prefer active voice.
- Show the problem, then the solution.
- Write for a smart but busy reader.

Example of bad copy:

> "AI English Journey is a revolutionary app that leverages cutting-edge AI to transform your language learning experience."

Example of good copy:

> "AI English Journey is the tool I built to replace a tutor I could not afford. It turns daily practice into structured progress toward fluency."

## 22. Prompt Engineering Rules

- Start prompts with context and goal.
- Be specific about output format.
- Provide examples when useful.
- Iterate rather than expecting perfection in one shot.
- Save high-quality prompts as reusable templates.
- Review AI output critically before using it.
- Use system prompts to establish role and constraints.

# VISUAL

## 23. Design Philosophy

The visual language is inspired by:

- Apple — precision, restraint, quality.
- Linear — clarity, speed, developer focus.
- Notion — whitespace, structure, calm.
- Raycast — command-driven, modern, dark-first.
- Vercel — technical, minimal, confident.
- Stripe — trust, detail, professionalism.
- Framer — motion, craft, creativity.

Core principles:

- Minimalism
- Generous whitespace
- Strong typography
- Subtle, purposeful motion
- Consistent color logic
- No decoration without function

## 24. Visual Identity

The identity should feel like a young, serious product company.

- Clean geometry
- Neutral base with one accent
- No gradients unless intentional and rare
- No stock illustrations
- Custom-feeling, even when simple

## 25. Color System

### Base Palette

| Role | Value | Usage |
|------|-------|-------|
| Background Primary | `#0A0A0A` or `#FFFFFF` | Main canvas |
| Background Secondary | `#111111` or `#F5F5F5` | Cards, sections |
| Text Primary | `#FFFFFF` or `#0A0A0A` | Headings, body |
| Text Secondary | `#A1A1AA` or `#52525B` | Captions, meta |
| Border | `#27272A` or `#E4E4E7` | Dividers, outlines |

### Accent Palette

| Role | Value | Usage |
|------|-------|-------|
| Accent | `#6366F1` | Primary actions, links, highlights |
| Accent Hover | `#4F46E5` | Hover states |
| Success | `#22C55E` | Positive states |
| Warning | `#EAB308` | Alerts |
| Error | `#EF4444` | Errors |

Default mode: dark. Light mode is optional but must be equally polished.

## 26. Typography

Primary typeface: **Inter** or **Geist**.

Monospace: **JetBrains Mono** or **Geist Mono**.

### Scale

| Level | Size | Weight | Usage |
|-------|------|--------|-------|
| Display | 48–72px | 700 | Hero |
| H1 | 36–48px | 700 | Page titles |
| H2 | 24–32px | 600 | Section titles |
| H3 | 18–20px | 600 | Subsections |
| Body | 16px | 400 | Main text |
| Caption | 13–14px | 400 | Meta, labels |
| Code | 14px | 400 | Inline and blocks |

Rules:

- Use a clear type scale.
- Limit to two typefaces.
- Prefer tight line-height for headings (1.1–1.2).
- Use comfortable line-height for body text (1.5–1.7).

## 27. Iconography

- Use a single icon library across all projects.
- Default: **Lucide** or **Phosphor Icons**.
- Icons must be consistent in weight and size.
- Avoid mixing icon styles.
- Use icons to support meaning, not replace labels.

## 28. Motion Principles

Motion should feel responsive and calm, not theatrical.

- Fast transitions: 150–250ms
- Entrance animations: subtle fade and slide
- Use motion to guide attention, not decorate
- Respect `prefers-reduced-motion`
- Avoid bouncing, spinning, or flashing effects

## 29. UI Principles

- Every element must have a reason to exist.
- Prioritize content over chrome.
- Maintain consistent spacing using a 4px or 8px grid.
- Use rounded corners sparingly and consistently.
- Buttons and interactive elements must have clear states.
- Forms should be minimal and forgiving.

## 30. UX Principles

- Start with the user's goal, not the feature list.
- Reduce cognitive load.
- Provide clear feedback for every action.
- Design for edge cases and empty states.
- Make the next step obvious.
- Test flows by asking: "Would I use this myself?"

# PROJECTS

## 31. Project Selection Rules

A project deserves to enter the ecosystem only if it meets most of these criteria:

- It solves a real problem I personally experience or deeply understand.
- I would use it myself.
- It can be shipped with professional design and documentation.
- It strengthens the overall narrative.
- It is not a copy of a tutorial or common portfolio cliché.
- It fits within my capacity to finish.

## 32. Portfolio Evaluation Checklist

Before any project is considered public-ready, verify:

- [ ] Solves a real problem
- [ ] I would use it myself
- [ ] Looks like a finished product
- [ ] Has a strong README
- [ ] Has architecture documentation
- [ ] Has a roadmap
- [ ] Has screenshots or demo
- [ ] Has clear features list
- [ ] Follows the design system
- [ ] Uses consistent writing style
- [ ] Improves the overall portfolio
- [ ] Has no placeholder text or broken links

If several items are unchecked, the project stays in development.

## 33. Repository Structure

Every repository should follow a clean, predictable structure:

```
project-name/
├── README.md
├── LICENSE
├── .gitignore
├── docs/
│   ├── architecture.md
│   ├── roadmap.md
│   └── assets/
├── src/
│   └── ...
├── tests/
│   └── ...
├── public/
│   └── screenshots/
└── .github/
    └── workflows/
```

Adjust by project type, but keep core files consistent.

## 34. Folder Naming

- Lowercase with hyphens: `docs/assets`, `src/components`
- No spaces or special characters
- Be descriptive but concise
- Use consistent pluralization

## 35. Commit Convention

Use conventional commits:

```
feat: add user authentication
fix: resolve login redirect issue
docs: update installation guide
refactor: simplify dashboard layout
test: add unit tests for parser
chore: update dependencies
```

Rules:

- Write in imperative mood: "add", not "added".
- Keep the summary under 50 characters.
- Use the body for explanation when needed.

## 36. GitHub Standards

- Profile README must match the personal narrative.
- Each repo must have a description, topics, and website link.
- Use pinned repositories to highlight the best work.
- Keep commit history clean and meaningful.
- Enable issues and discussions only if actively maintained.
- Use consistent naming: lowercase, descriptive, no emojis in repo names.

## 37. README Standards

Every README must follow the detailed [`README_STANDARD.md`](./README_STANDARD.md) and the [`PROJECT_STORY_FRAMEWORK.md`](./PROJECT_STORY_FRAMEWORK.md).

At minimum, every README must include:

1. Project name and one-line description
2. Problem statement
3. Why I built it
4. Solution overview
5. Key features
6. Screenshots or demo
7. Architecture
8. Installation
9. Usage
10. Roadmap
11. FAQ
12. Contributing
13. License

Style: clear, honest, no clichés. Write as if for Linear or Vercel. No mentions of "portfolio" or "admission" in project READMEs.

## 38. Documentation Standards

- Docs live in the `docs/` folder when possible.
- Use Markdown.
- Include diagrams for architecture and flows.
- Keep language consistent with the writing style.
- Update docs when code changes.

## 39. Architecture Standards

- Document the high-level architecture in `docs/architecture.md`.
- Use diagrams: system overview, data flow, key components.
- Keep diagrams simple and readable.
- Explain why architectural decisions were made.
- Use clear component and service names.
