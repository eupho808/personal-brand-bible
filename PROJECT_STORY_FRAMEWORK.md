# Project Story Framework

> How every project in the ecosystem tells its story.

This document defines the narrative structure for every project README, case study, and portfolio page. It ensures that all projects sound like chapters of one story, not separate marketing pieces.

---

## Core Idea

Every project must answer one question:

> What real problem did I encounter, and how did I solve it?

The story is not about technology. It is about the journey from problem to solution.

---

## Narrative Arc

Every project story follows this arc:

### 1. Problem

- Describe the real situation.
- Make it specific and personal when possible.
- Avoid abstract or universal statements.

Example:  
*"Private English tutors cost more than I can afford, and most apps either gamify vocabulary without building fluency or treat every learner the same."*

### 2. Why I Built It

- Explain why existing solutions did not work.
- Connect the problem to your own experience.
- Show motivation without mentioning university or portfolio.

Example:  
*"I needed a system that could replace a tutor for my own exam preparation — structured, adaptive, and affordable."*

### 3. Solution

- Describe what you built at a high level.
- Focus on approach, not implementation details.
- Explain what makes it different.

Example:  
*"AI English Journey is a learning operating system. It combines structured lessons, adaptive algorithms, and AI assistance to guide one learner from A1 to exam readiness."*

### 4. What It Does

- List key capabilities.
- Each item should connect back to the problem.
- Use verbs, not nouns.

Example:
- Structures daily learning paths by level and goal.
- Adapts difficulty based on actual performance.
- Tracks progress toward exam readiness.
- Explains mistakes with AI-generated feedback.

### 5. How It Works

- Short technical overview.
- Architecture, stack, or key design decisions.
- Link to deeper docs when needed.

### 6. Current Status

- Be honest about where the project is.
- Mention shipped parts and parts in progress.
- Do not pretend an MVP is a finished product.

Example:  
*"The architecture and Phase 0 backend are complete. The adaptive learning engine and frontend are in development."*

### 7. What I Learned

- Optional for README, required for case studies.
- One or two concrete insights.
- Shows growth and reflection.

Example:  
*"Building this taught me that AI is most useful as a feedback layer, not as the core learning logic."*

### 8. What Is Next

- Roadmap or future direction.
- Keep it realistic.
- Connect to the larger ecosystem when relevant.

---

## Tone and Style

- First person when the project is personal: *"I built...", "I needed..."*
- Third person only when describing technical behavior: *"The engine evaluates..."*
- Active voice.
- Short paragraphs.
- No exaggeration.
- Honest about limitations.

---

## Forbidden Phrases

Never use:

- "This project was built for my portfolio."
- "This project was created for university admission."
- "I made this to impress recruiters."
- "This is just a demo."
- "In today's rapidly changing world..."
- "Leveraging the power of AI..."
- "Revolutionary / game-changing / cutting-edge"

---

## Connection to Personal Brand

Every project story must reinforce the overall narrative:

> A young AI Product Builder identifies real problems in his own life, designs thoughtful solutions, and ships them as part of one coherent ecosystem.

When possible, connect the project to other projects:

- AI English Journey came from a personal need.
- WalletGuard Pro came from a real security concern.
- AI Project Architect Design came from the need to structure ideas into real products.
- All of them are documented in the Personal Operating Manual.

---

## Template for Case Study

A case study expands the README with deeper narrative:

1. **Context** — situation before the project.
2. **Challenge** — what made the problem hard.
3. **Process** — how I approached it.
4. **Solution** — what I built.
5. **Results** — what changed.
6. **Learnings** — what I discovered.
7. **Next Steps** — where it goes.

---

## Review Checklist

Before publishing any project story:

- [ ] Problem is real and specific
- [ ] Motivation is personal but not portfolio-focused
- [ ] Solution is clearly described
- [ ] Features connect to the problem
- [ ] Status is honest
- [ ] Tone matches the brand
- [ ] No forbidden phrases
- [ ] Story connects to the larger ecosystem
- [ ] Reader understands why this project exists
