# README Standard

> Single standard for every README in the ecosystem.

This document defines how every project README must be written, structured, and formatted. No README should be created or updated without following this standard.

---

## Purpose

A README is not a technical dump. It is the first thing a visitor sees. It must communicate:

1. What problem the project solves.
2. Why it exists.
3. What it does.
4. How to use it.
5. Where it is going.

Every README is a story first, documentation second.

---

## Language

- **English only.** No Russian, no mixed languages.
- Natural, clear, professional.
- No clichés: revolutionary, game-changing, cutting-edge, leverage, synergy, disruptive.
- No hype, no superlatives without proof.
- No filler: "In today's world...", "With the rise of AI...", "We are excited to..."
- Active voice preferred.
- Short sentences. One idea per sentence.

---

## Tone

- Confident but humble.
- Honest about limitations and status.
- Personal when relevant — the project comes from a real problem.
- Professional, not corporate.

---

## Required Structure

Every README must include the following sections in this order:

### 1. Project Title

- One line.
- Clear, descriptive, no buzzwords.
- Example: `AI English Journey` — not `AI English Journey: The Future of Language Learning`.

### 2. One-line Description

- One sentence under the title.
- Explains what the project does.
- Example: `A learning operating system that guides one student from beginner English to exam readiness.`

### 3. Problem Statement

- 2–4 sentences.
- Real problem, real context.
- Personal if applicable.
- No mention of university admission or portfolio.

### 4. Why I Built It

- 2–4 sentences.
- Connects the problem to the author.
- Explains motivation without clichés.

### 5. Solution Overview

- 3–5 sentences.
- What the project does differently.
- Core approach or philosophy.

### 6. Key Features

- Bullet list, 4–8 items.
- Each feature starts with a verb.
- Explain benefit, not just capability.

### 7. Screenshots or Demo

- At least one screenshot or demo link.
- Must be real, not placeholder.
- Use concise captions.

### 8. Architecture

- Short overview or link to `docs/architecture.md`.
- 3–6 bullet points or a diagram.
- Avoid over-explaining.

### 9. Installation

- Step-by-step commands.
- Assumes reasonable defaults.
- Test the commands before publishing.

### 10. Usage

- Basic usage example.
- Link to full docs if needed.

### 11. Roadmap

- 3–5 items.
- Current status and next steps.
- Use checkboxes.

### 12. FAQ

- 2–5 common questions.
- Honest answers.

### 13. Contributing

- Short guidelines.
- Link to `CONTRIBUTING.md` if it exists.

### 14. License

- License name and link.

## Formatting Rules

### Headings

- Use ATX style: `#`, `##`, `###`.
- Title case for H1 and H2.
- Sentence case for H3 and below.

### Lists

- Use dashes `-` for unordered lists.
- Use `1.` for ordered lists.
- Keep list items parallel in structure.

### Code

- Use fenced code blocks with language tags.
- Keep examples short and runnable.
- Explain what the command does.

### Links

- Use descriptive link text.
- Avoid raw URLs in body text.

### Emphasis

- Use **bold** for key terms.
- Use `code` for file names, commands, variables.
- Avoid italic for long phrases.

### Tables

- Use only when comparing several items.
- Keep columns narrow.
- Left-align text, right-align numbers.

### Emojis

- **No emojis in project READMEs.**
- Exception: flags in University Strategy documents.
- Profile README may use minimal, intentional emojis.

### Badges

- Optional.
- If used, keep them minimal and truthful.
- No fake badges (e.g., "audited by" if not audited).

---

## Length

- Target: 500–1500 words.
- Never longer than necessary.
- Every section must earn its place.

---

## Meta Rules

- No mention of "portfolio", "admission", or "university" in project READMEs.
- No phrases like "This project was built to demonstrate..."
- No lists of technologies without context.
- No copied template text.
- Every README must be proofread before publication.

---

## Example Opening

```markdown
# AI English Journey

> A learning operating system that guides one student from beginner English to exam readiness.

## Problem

Learning English to the level required by international exams is expensive. Private tutors cost more than I can afford, and most apps either gamify vocabulary without building real fluency or treat every student the same.

## Why I Built It

I needed a system that could replace a tutor for my own preparation. I wanted structured lessons, adaptive practice, and clear progress tracking — all in one place.

## Solution

AI English Journey is not a chatbot. It is a learning operating system that combines structured content, adaptive algorithms, and AI assistance to guide a single learner from A1 toward B2/C1 and exam readiness.
```

## Review Checklist

Before marking a README as complete:

- [ ] Follows this structure
- [ ] Written in clear English
- [ ] Contains no clichés or hype
- [ ] Explains the real problem
- [ ] Explains why the author built it
- [ ] Has screenshots or demo
- [ ] Installation commands are tested
- [ ] Roadmap is realistic
- [ ] No placeholder text
- [ ] Matches the visual style of the ecosystem
- [ ] Would impress an admission committee or employer
